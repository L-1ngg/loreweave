# P01: Archive legacy code and prepare a clean construction baseline

**Status:** published snapshot; the live GitHub work item owns execution state.

**Live work item:** [#30](https://github.com/L-1ngg/loreweave/issues/30)

## Parent

[Spec #29](https://github.com/L-1ngg/loreweave/issues/29)

## What to build

A maintainer can restore an archive of the existing work/data, remove the retired implementation from the active repository, then start and validate a clean local TypeScript construction entry. Archive verification and cleanup finish before replacement feature work; this is the prefactoring prerequisite, not a finished product feature.

## Acceptance criteria

- [ ] Record a recovery manifest covering actual tracked changes, untracked files, current revision and existing database/artifacts; preserve the archive outside the active repository and demonstrate restoration in an isolated location before deleting retirement candidates.
- [ ] Keep private credentials/data in private recovery storage and preserve unrelated user work, current design contracts and attributable history/notices.
- [ ] Inventory and remove retired Forge/Pi, Wiki/graph/entity and embedding/vector/RRF source, vendored runtime, exclusive dependencies, adapters, dedicated tests and fixtures, schema definitions, migrations and development/evaluation scripts from the active construction tree.
- [ ] Rewrite default package, build/typecheck/test, configuration and CI targets for the new baseline; ordinary repository searches and execution must not discover or load a retained legacy runtime directory.
- [ ] Archive or clearly mark old runtime/design instructions, resolve historical source links through the recovery baseline and keep active guidance focused on the replacement.
- [ ] Provide root-script-owned local startup/build/typecheck/validation entries and a fresh PostgreSQL schema/database path; preserve old data independently and do not apply retired migrations, automatically migrate old knowledge data or implicitly load old configuration.
- [ ] Establish TanStack Start/React 19+, Router, Query and Form on Bun/Vite with PostgreSQL/Drizzle; replace the default independent Hono entry and verify a small text-layer PDF extraction fixture under the selected runtime.
- [ ] Resolve and lock a compatible Start/Router/Query/Form, AI core/provider/React/persistence/MCP and Intent package set using published skills/source; record package/runtime versions and upstream license/provenance evidence.
- [ ] A controlled-provider probe verifies tool calling, typed output, persistence contract shape, generation with zero subscribers and replay of the same run without a second model call.
- [ ] Default construction startup and checks cannot execute paid-provider work or connect to the old data implicitly; fixtures and real-provider entry points are explicit.
- [ ] Verify the clean baseline and removal inventory before any dependent ticket starts; self-hosted application deployment packaging is not added.

- [ ] Minimal integration probes cover dev/build/compiled Bun entry, protected Start server functions, Query SSR hydration, server-only bundle boundaries, multipart fixture upload, authorized PDF GET/HEAD/Range, unbuffered SDK SSE and official MCP-client transport initialization.
- [ ] Install Intent as a local development tool, discover and load the selected packages' shipped skills, inspect generated mappings with --dry-run and preserve project instructions when applying them.
- [ ] Record any demonstrated adapter gap and the maintained alternative selected; retain a narrow Hono adapter only with concrete compatibility evidence.
